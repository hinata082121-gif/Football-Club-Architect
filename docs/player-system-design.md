# Football Club Architect Player System Design

## 概要

選手システムは、クラブ経営ゲームとしてのリアリティを高め、スカウトAI、監督AI、練習試合、世代交代をゲームの中核に接続するための拡張です。

現在のMVPでは、チームの強さは主に `club.teamPower`、`club.teamwork`、`club.condition` で表現されています。選手システム導入後は、個別選手の能力、年齢、状態、契約、起用状況からチーム戦力を算出し、クラブ運営の意思決定がより具体的に試合結果へ反映される構造にします。

このゲームのプレイヤーは監督ではなくクラブ社長です。そのため、プレイヤーが毎試合のスタメンを細かく手動指定するのではなく、補強方針、予算、委託範囲、最終承認を担います。現場の選手選考は監督AI、候補発掘はスカウトAI、契約交渉や放出整理は将来的な強化担当AIへ委託できる設計にします。

役割の基本方針:

- プレイヤー: 経営判断、方針設定、予算配分、重要な承認を行う
- 監督: スタメン、ベンチ、起用方針、若手起用、試合での選手運用を行う
- スカウト: 獲得候補の発掘、能力推定、将来性推定、リスク評価を行う
- 強化担当: 契約交渉、放出候補整理、年俸総額管理、移籍市場対応を行う

## 役割分担

### プレイヤーが行うこと

- 補強予算の決定
- 重点補強ポジションの決定
- 若手重視か即戦力重視かの方針決定
- 獲得候補の最終承認
- 放出候補の最終承認
- 契約更新方針の決定
- 監督やスカウトへの委託範囲の設定

プレイヤーは「誰を発掘するか」「誰を起用するか」を細かく毎回操作するよりも、「どの方向へクラブを育てるか」を決めます。重大な補強、放出、高額契約はAIが勝手に確定せず、承認待ちログとして提示する方針を維持します。

### 監督が行うこと

- スタメン選考
- ベンチ選考
- 起用方針の判断
- 若手起用
- コンディション管理
- 試合での選手起用

監督AIは `Coach.playerSelection`、`Coach.development`、`Coach.motivation`、`Coach.aiJudgment` を使って、現在の選手層とクラブ方針に合う起用を行います。プレイヤーは起用方針を設定し、監督へどこまで委任するかを決めます。

### スカウトが行うこと

- 候補選手の発掘
- 能力推定
- 将来性推定
- 年俸・移籍費の推定
- リスク評価
- クラブ方針に合う選手の探索

スカウトAIは `Staff.role === "scout"` のスタッフを拡張して扱います。能力が高いほど、クラブに合う候補を見つけやすく、能力推定の誤差も小さくなります。

### 強化担当が将来的に行うこと

- 契約交渉
- 放出候補整理
- 年俸総額管理
- 移籍市場対応

MVP/α版では強化担当を既存スタッフroleに追加するか、`sales` や `analyst` と兼務させる簡易実装から開始できます。本格実装時は `sporting_director` や `director` のようなroleを追加する余地があります。

## 選手データ設計

MVP/α版では、まず軽量な `Player` 型で開始します。選手個別の細かいスキルやポジション適性は後回しにし、経営判断に必要な値だけを持たせます。

```ts
export type PlayerPosition = "GK" | "DF" | "MF" | "FW";

export type PlayerStatus =
  | "starting"
  | "bench"
  | "reserve"
  | "injured"
  | "transfer_listed"
  | "leaving"
  | "retired";

export interface Player {
  id: string;
  name: string;
  age: number;
  position: PlayerPosition;
  overall: number;
  potential: number;
  growth: number;
  condition: number;
  morale: number;
  salary: number;
  contractMonths: number;
  marketValue: number;
  status: PlayerStatus;
  isHomegrown: boolean;
  joinedAtYear: number;
  joinedAtMonth: number;
}
```

追加候補:

- `leadership`: ベテランや主将候補の価値を表現する
- `injuryRisk`: 怪我しやすさを表現する
- `popularity`: ファン増加、グッズ収入、スター性に影響する
- `loyalty`: 契約更新や移籍希望に影響する
- `developmentStage`: 若手、成長期、全盛期、ベテランなどの表示用
- `retirementRisk`: 高齢選手の引退確率に影響する

初期実装では複雑にしすぎず、`overall`、`potential`、`growth`、`age`、`condition`、`salary`、`status` を中心に進めます。

## 年齢制度

1ターンを1か月として扱う既存の進行に合わせ、選手は12か月ごとに年齢が上がります。

年齢帯ごとの特徴:

- 16〜20歳: 能力は低いが成長性が高い。練習試合や若手起用で伸びやすい
- 21〜24歳: 成長期。獲得価値が高く、クラブの中核候補になる
- 25〜29歳: 全盛期。能力が安定し、公式戦で計算しやすい
- 30〜33歳: 経験はあるが成長は鈍化する。短期戦力として有効
- 34〜36歳: 衰退開始。高年俸の場合は世代交代や放出判断が必要
- 37歳以上: 引退リスクが高い。戦力維持には後継選手の準備が必要

この年齢制度により、先行プレイヤーが強力な選手を集めても、その戦力は永久には固定されません。上位クラブほど高年俸と世代交代リスクを抱え、後発プレイヤーは若手発掘、育成、練習試合で追いつく余地を得ます。

## 選手成長・衰退

### 若手

若手は `growth`、`potential`、出場機会、練習試合経験に応じて `overall` が上がります。監督の `development` が高いほど、若手起用時の成長効率が良くなります。

### 全盛期

25〜29歳前後の選手は能力が安定しやすく、公式戦で信頼できます。一方で成長幅は若手より小さく、コンディション管理が重要になります。

### ベテラン

30歳以上の選手は `overall` が徐々に下がる可能性があります。ただし、将来的に `morale`、`leadership`、`loyalty` を導入すれば、若手の成長補助、チーム安定、試合レポート上の良い影響を持たせられます。

### 高齢選手

34歳以上は衰退、怪我、引退リスクが高まります。高年俸の高齢選手を抱え続けるか、若手へ投資するかが経営判断になります。

## スカウト機能

スカウト機能は、候補選手を自動生成し、プレイヤーに「承認するかどうか」を提示する仕組みです。スカウトAIは候補選手の実能力を完全には見抜けず、能力値には推定誤差を持たせます。

### スカウトの探索方針

- 若手重視
- 即戦力重視
- 低コスト重視
- 高ポテンシャル重視
- 特定ポジション重視
- 地元選手重視
- データ重視

探索方針はクラブ方針 `ClubPolicy` と連動させます。たとえば `youth_development` は若手重視、`win_now` は即戦力重視、`local_first` は地元選手重視、`data_driven` は推定精度やコスパ重視に寄せます。

### スカウトAIの能力による差

- `judgment` が高いほど、クラブ状況に合う候補を見つけやすい
- `specialty` が高いほど、候補の質が上がる
- `aiAccuracy` が高いほど、能力推定の誤差が小さくなる
- 低能力スカウトは過大評価選手やミスマッチな候補を出す可能性がある
- ただし低能力スカウトでも、安価な掘り出し物を見つける可能性がある

ストレス軽減のため、低能力スカウトの失敗は即破滅ではなく「費用対効果が低い」「成長に時間がかかる」「方針と少しずれる」程度から始めます。高額移籍や高年俸契約は承認制にします。

## チーム編成画面

チーム編成画面は、プレイヤーがクラブの人員構成を把握し、監督やスカウトへの方針を決めるための画面です。

表示するもの:

- 所属選手一覧
- ポジション
- 年齢
- 総合能力
- 将来性
- コンディション
- 士気
- 年俸
- 契約残り月数
- 起用状態
- 放出候補設定
- 獲得候補一覧
- チーム年齢構成
- ポジション別人数
- 年俸総額
- チーム戦力

初期UIでは一覧と集計カードを優先します。詳細なフォーメーションボードや選手個別履歴は後続Phaseで追加します。

## 監督への起用委託

監督には、選手起用方針を委託できます。プレイヤーは細かいスタメン操作ではなく、起用ポリシーを設定します。

```ts
export type CoachSelectionPolicy =
  | "best_overall"
  | "youth_development"
  | "condition_first"
  | "balanced"
  | "veteran_stability"
  | "rotation";
```

委託方針:

- `best_overall`: 総合能力を最優先する
- `youth_development`: 若手の出場機会を増やす
- `condition_first`: コンディションの良い選手を優先する
- `balanced`: 能力、年齢、状態をバランスよく見る
- `veteran_stability`: 経験ある選手を重視する
- `rotation`: 疲労を分散し、控え選手にも出場機会を与える

監督能力による差:

- `playerSelection` が高いほど適切なスタメンを選べる
- `development` が高いほど若手起用時の成長効率が良い
- `motivation` が高いほど士気を維持しやすい
- `aiJudgment` が高いほどチーム状況に合う起用ができる

監督AIの判断理由はActionLogまたは専用レポートに残します。たとえば「若手育成方針により19歳MFをベンチ入り」「コンディション低下により主力FWを温存」のように、プレイヤーが納得できる説明を出します。

## 後発救済との関係

選手システムは、対戦型ゲームとしての長期バランスにも重要です。

- 選手は年齢で衰退・引退するため、先行プレイヤーの戦力が永久固定されない
- 若手発掘で後発プレイヤーが追い上げられる
- 小規模クラブには若手育成の余地がある
- 練習試合で若手を育てられる
- 上位クラブは高年俸・世代交代リスクを抱える
- スカウト精度によって低コスト補強が可能になる

上位クラブは短期的な強さを維持しやすい一方で、年俸総額、契約更新、高齢化、引退リスクを管理する必要があります。後発クラブは若手発掘、低コスト補強、練習試合育成によって、中長期的に差を詰める設計にします。

## 実装優先度

### 優先度高

1. `Player` 型の追加
2. 初期選手生成
3. チーム編成画面
4. チーム戦力を選手から算出
5. スカウト候補生成
6. 選手獲得承認

### 優先度中

7. 監督への起用委託
8. 年齢・成長
9. 衰退
10. 契約月数
11. 年俸総額管理

### 優先度低

12. 引退
13. 移籍オファー
14. 選手不満
15. 怪我詳細
16. ポジション適性詳細

## 既存コードへの接続方針

今後変更が必要になる主な場所:

- `src/types/game.ts`: `Player`、`PlayerPosition`、`PlayerStatus`、`CoachSelectionPolicy`、獲得候補型を追加する
- `src/game/initialState.ts`: 初期選手生成と初期スカウト候補生成を追加する
- `src/game/balance.ts`: 年齢帯、成長率、衰退率、年俸、移籍費、候補生成の数値を集約する
- `src/game/playerActionEngine.ts`: 既存の `recruit_player` を、将来的に候補選手の承認フローへ置き換える
- `src/game/staffAIEngine.ts`: scout roleの行動を、候補選手生成と能力推定へ接続する
- `src/game/matchEngine.ts`: `club.teamPower` 直接参照から、選手編成に基づく戦力算出へ段階移行する
- `src/game/trainingMatchEngine.ts`: 練習試合経験を若手成長、監督育成、連携向上へ接続する
- `src/components/screens`: チーム編成、スカウト候補、契約承認の画面を追加する

段階移行のため、初期実装では `club.teamPower` を残したまま、選手から算出した値を同期する方法が安全です。その後、試合計算の参照元を `calculateTeamPowerFromPlayers(players)` のような関数へ移していきます。
